# Relay NW data-retention inventory

Last technical audit: 2026-08-06. This inventory describes implemented behavior; it is not a claim of legal compliance.

| Data | Relay/Twilio copies | Established policy and implemented control | Unresolved decision |
| --- | --- | --- | --- |
| Leads | `leads`, including caller identity, intake text, notes and delivery metadata | No time period is established. Tenant-scoped operator export includes the rows. Authorized closed-account deletion removes them transactionally. | Set a retention period and decide whether soft-deleted leads expire sooner. |
| SMS content | Inbound bodies are duplicated in `inbound_messages` and `messages`; outbound bodies are in `messages`; Twilio holds Message resources; notification email/SMS providers may receive a copy | `INBOUND_MESSAGE_RETENTION_DAYS` (default 90) applies to inbound bodies. The daily job requests deletion of each expired Twilio Message, then nulls both Relay copies even if the provider request partly fails; metadata/SID remains for retry and audit. No outbound-body period is established. | Counsel/operator must set outbound retention and decide what can be done about already-delivered owner email/SMS copies and provider backups. |
| Calls | `calls.raw_summary` and call/phone/status metadata; some identifiers are copied into `leads` and Twilio | No time period is established. Closed-account deletion removes Relay call rows. | Set call-metadata retention and decide whether Twilio Call resources must be deleted or retained. |
| Voicemail recordings | Twilio Recording media; Relay stores SID/URL/metadata in both `leads` and `calls` and proxies playback without caching media | No time period is established. Closed-account deletion deduplicates SIDs and deletes Twilio Recordings before removing Relay references. Twilio 404 is treated as already deleted. A partial provider failure stops database deletion for retry. | Counsel must set the recording period and confirm notice/consent requirements by caller location and call flow. |
| Raw and displayed transcripts | `leads.voicemail_raw_transcript` and `leads.voicemail_transcript`; OpenAI processes submitted audio/text | No time period is established. Both fields are included in export and removed with the tenant transaction. | Set a transcript period and confirm whether raw text should be shorter-lived than displayed text. Confirm applicable OpenAI provider retention/configuration. |
| AI summary evidence | Summary, classification, exact transcript evidence excerpts, validation reasons and aggregate confidence metrics in `leads` | No time period is established. All content fields are removed with the lead/account. Aggregate metrics are not preserved separately. | Decide whether non-content quality metrics need an aggregate, de-identified evidence policy. |
| Webhook diagnostics | Sanitized `webhook_events`; related `provider_action_events` contain separate status/recovery evidence | `WEBHOOK_EVENT_RETENTION_DAYS` (default 30) deletes webhook rows daily. Payloads already omit full phone numbers, SMS bodies and recording URLs. Provider-action evidence has no period. | Set a period for provider-action diagnostics and Stripe webhook ledgers. |
| Audit events | `account_audit_events`, `platform_audit_events`, and content-free `data_retention_events` | No time period is established. Account deletion removes tenant account-audit rows and preserves a separate deletion event with UUID, actor, timestamp, outcome, failure category and counts—never message/transcript content. Platform events survive with their existing `ON DELETE SET NULL` behavior. | Counsel/operator must identify which audit evidence is required and for how long; summaries should be reviewed for incidental personal data before a policy is set. |
| Deleted accounts | Account row plus tenant tables, Supabase greeting objects, Twilio recordings/messages, Stripe/setup/platform references, and Supabase Auth users | Super-admin workflow supports JSON export, non-mutating preview, and confirmed deletion only after archived/closed state. Provider cleanup precedes an atomic tenant DB deletion. Repeats return `already_deleted`. Stripe/setup/platform foreign keys are nulled. Shared Supabase Auth identities are not deleted because one user can belong to multiple accounts. | Decide whether orphaned Auth identities are removed after checking all memberships; define handling of Stripe customer/subscription records and Twilio Call records; decide whether export must embed media bytes. |
| Replaced greeting files | Public objects under `account-greetings/{account_id}/`; current URL in `account_settings` | Each successful new recorded greeting lists only the tenant prefix and removes every object except the new file. Cleanup result is recorded; account deletion removes the whole tenant prefix. | Decide retry/alert timing for a storage cleanup failure and whether public greeting storage should become private/signed. |

## Job and operator boundaries

- `GET /api/cron/retention` is a dry run; `?execute=true` performs the two established operational policies. Production requires the cron bearer secret.
- `GET /api/ops/accounts/export?account_id=…` is super-admin-only and returns a no-store JSON package. It contains provider media references, not media bytes.
- `POST /api/ops/accounts/delete` defaults to dry run. Execution requires `mode=execute`, exact `confirmation=confirmed`, super-admin authorization, and archived/closed state.
- Destructive provider/database steps are tenant-scoped. The account-deletion core rejects any candidate carrying a different account ID before calling a provider.
- Retention/deletion action logs contain counts and failure categories only. They must not contain message bodies, transcript excerpts, phone numbers, or provider URLs.

## Questions requiring counsel

1. Which call-recording notice or consent flow is required for each supported state and for direct versus forwarded calls? Is the current voicemail greeting sufficient notice anywhere Relay operates?
2. What retention periods apply to recordings, raw transcripts, displayed transcripts, summary evidence, call/lead metadata, outbound SMS, opt-out records, audit records, and provider diagnostics?
3. Must any records be held for disputes, billing, litigation, security incidents, or regulatory requests, and how should an authorized hold suspend automated deletion?
4. What deletion obligations apply to Twilio Call records, Stripe records, email/SMS notifications already delivered to owners, OpenAI processing records, and provider backups?
5. What identity verification and authorization evidence is required before a business account export or deletion?
